## פער 1 (P1) — ביטול הו"ק יכול להישלח פעמיים ✅ נסגר

**הטענה:** הבעלות נבדקת *אחרי* הפעולה העסקית. שתי הודעות `כן` חופפות (message_id שונים) — שני ה-flows קוראים רישום פעיל והו"ק פעילה *לפני* שאחד מעדכן, ושניהם קוראים ל-`cancelRecurringPayment`. רק אחר כך אחת מסומנת stale. הגנת ה-rev לבדה לא הספיקה כי `performCancellation` רץ בתוך `processMessage`, לפני בדיקת הבעלות ב-`applyResult`.

**התיקון** — [flows.ts:769](../src/lib/bot/flows.ts:769): ה-UPDATE של `registrations` הפך ל-**compare-and-set** בפעולת DB אחת:
```
.update({ status: 'בוטל', notes: ... })
.eq('id', reg.id)
.in('status', ['מאושר', 'ממתין לאישור'])   // ← השומר האטומי
.select('id')
```
- 0 שורות שהוחזרו ⇒ מישהו כבר ביטל (הודעה חופפת) ⇒ `return null` — **לא** נוגעים ב-PayPlus שוב.
- שגיאת UPDATE ⇒ `return null` (מסלול גיבוי בטוח, בלי סליקה).
- כך **הפעולה העסקית עצמה אטומית**, לא רק שמירת מצב השיחה. גם שני message_id שונים לא מבצעים אותה פעמיים, וגם בקשה שהפכה למיושנת בזמן `processMessage` לא מבצעת ביטול חיצוני שני.

**קריטריון קבלה (שני "כן" חופפים → לכל היותר ביטול חיצוני אחד):** מכוסה. בדיקה `Gap1 (S1)` מריצה שתי POST חופפות עם `Promise.all` מול DB מצבי; המוק של `registrations.update` נאמן ל-Postgres (מחיל UPDATE רק אם *כל* המסננים מתקיימים). תוצאה: `cancelRecurringPayment` נקרא **פעם אחת בלבד**, הרישום בוטל פעם אחת. **fail-before מוכח**: כשמסירים את `.in('status', ...)` — `ppCalls=2`.

**הערה על התאוששות מכשל חלקי (update הצליח, קריאת ספק נכשלה):** ה-UPDATE קודם לקריאת PayPlus, וכשל הספק לא מסמן את הרישום בחזרה כפעיל. זו נותרה סמנטיקת at-least-once לקריאת הספק (כמו חריג E) — עדיין פתוח כהחלטת מוצר, ראה למטה. אין כפל-ביצוע של ה-UPDATE; מה שלא הובטח הוא reconciliation מלא של קריאה שאבדה.

## פער 2 (P2) — מדיה מסמנת הצלחה למרות כשל מחיקה ✅ נסגר

**הטענה:** הערך המוחזר מ-`clearSessionIfCurrent` לא נבדק, והאירוע סומן `processed` כבר בעת הודעת הקבלה — לפני סיום ניתוח הרקע.

**התיקון** — [route.ts:443](../src/app/api/webhooks/manychat/route.ts:443) בתוך `finishMediaInBackground`:
```
const cleared = await clearSessionIfCurrent(supabase, phone, rev)
if (cleared.error) { releaseClaim(messageId, claimToken) }   // כשל מחיקה → retry, לא מסמנים הושלם
else               { markProcessed(messageId, claimToken) }  // הושלם רק עכשיו, בסוף הרקע
```
- `markProcessed` הועבר ל**אחרי** שעבודת הרקע (כולל המחיקה) הסתיימה בהצלחה — הופרד בין קבלה (ה-ack המיידי) להשלמת עיבוד.
- כשל מחיקה ⇒ התפיסה משוחררת ⇒ ניסיון חוזר יכול לעבד. ניתוח המדיה עצמו at-least-once (מתועד).

**קריטריון קבלה:** בדיקה `Gap2` — DB מוגדר `failClear`, ניתוח המדיה מוחלף בתוצאה קבועה. תוצאה: האירוע **לא** מסומן `processed`, והתפיסה **משוחררת** (זמין ל-retry).

## פער 3 (P2) — חידוש תפיסה מוחק אירוע שהושלם בינתיים ✅ נסגר

**הטענה:** ה-DELETE של החידוש הותנה רק ב-`session_id` ולא ב-`processed=false`. אם העובד המקורי מסיים ומסמן `processed=true` בין ה-SELECT ל-DELETE — המחיקה עדיין תואמת ומוחקת אירוע שהושלם.

**התיקון** — [route.ts claimMessage](../src/app/api/webhooks/manychat/route.ts:216): ה-DELETE של החידוש הותנה גם ב-`.eq('processed', false)`, ושגיאת מחיקה (`delErr`) מובחנת מ-0-שורות (כפילות אמיתית) ולא נבלעת כ-`duplicate`.

**קריטריון קבלה (הושלם בין SELECT ל-DELETE → לא מעבדים מחדש):** בדיקה `Gap3` — מוק שמחזיר ב-SELECT snapshot ישן (`processed=false`) אך מסמן מיד `processed=true` (מדמה את העובד המקורי שסיים). תוצאה: ה-DELETE המותנה-`processed=false` לא תואם ⇒ `duplicate` ⇒ `processMessage` **לא** נקרא שוב (`calls=0`).
